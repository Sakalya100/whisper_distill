Hinglish dictation on free Kaggle

Distilling a 132M on-device dictation model from a Hindi Whisper teacher, on a shared 30‑hour weekly GPU quota. The plan is ordered by what has to be measured before the rest of it means anything — two gates up front, then a schedule that survives a session disconnect.

Gate 0 — measure

How does Kaggle bill a T4×2 session?

The 30 hours is one pool shared across P100 and T4×2. Nothing in Kaggle's docs or product announcements says whether the meter charges session wall‑clock or GPU‑hours. That single fact moves the schedule by about 2×, so it is worth 30 minutes of quota to settle it before planning anything else.

Unverified · 30 min of quota

The procedure

  1. Verify your phone number on Kaggle first. It gates both accelerators and notebook internet — without it the GPU dropdown is greyed out and this experiment can't start.
  2. Open kaggle.com/settings (or the notebook editor sidebar) and write down the exact GPU hours already used this week. Screenshot it — the meter rounds, and you want the before value in writing.
  3. New notebook → Accelerator: GPU T4 ×2. One cell: import torch, time; print(torch.cuda.device_count()); time.sleep(900) with a print every 60 s so the cell never goes silent.
  4. Run it as Save & Run All (Commit), not in the interactive tab. This is what you'll use for every real run, so measure the thing you'll actually be billed for.
  5. While it runs, try to start a second GPU session. Whether it queues, refuses, or runs tells you the concurrency cap — free information from the same experiment.
  6. When the commit finishes, re-read the meter. Also start a CPU‑only notebook for 15 minutes and check the GPU meter again afterwards — this confirms the assumption that CPU sessions are free, which the whole workflow below leans on.
+15 min
Wall‑clock billing. A 12‑hour T4×2 commit costs 12 quota‑hours and yields ~24 GPU‑hours. Run everything as DDP inside one dual‑GPU session; never two concurrent single‑GPU sessions, which would bill twice for the same work.
+30 min

Gate 1 — audit

Can the teacher actually write English?

This is the finding that reordered the plan. IndicWhisper is not a Hugging Face repo — Vistaar ships hindi_models.zip from e2enetworks object storage, and a community issue asking how to load it has been open since April 2024. The HF‑native substitute is vasista22/whisper-hindi-medium: whisper‑medium base, Speech Lab IIT Madras, 6.82 WER on FLEURS, 80 mel bins — so the shared feature‑extraction decision survives.

Project‑blocker class · ~1 h of quota

Why it can't wait for the smoke test

That checkpoint was fine‑tuned on GramVaani, ULCA, Shrutilipi and FLEURS — four corpora that are entirely Devanagari, normalised and unpunctuated. If the teacher transliterates Latin‑script English instead of preserving it, then every pseudo‑label is wrong in precisely the dimension a Hinglish dictation model exists to serve, and no student‑side fix recovers it. The same corpora also mean the teacher may have no punctuation to donate — which is the premise of the whole pseudo‑labelling argument.

The test

Run the candidate over 30 minutes of genuinely code‑mixed speech and read the output with your own eyes. One utterance decides it:

SpokenPassFail
“meeting chaar baje hai, Slack pe ping karo” meeting 4 baje hai, Slack pe ping karo मीटिंग चार बजे है, स्लैक पे पिंग करो
Latin‑script Slack surviving is the signal. The chaar → 4 conversion is not the model's job — that belongs in rule‑based inverse text normalisation downstream.
Blocks Your mel configuration. If the audit fails, the teacher reopens to openai/whisper-large-v3 or ARTPARK-IISc/whisper-large-v3-vaani-hindi — both 128 mel, which forfeits single‑pass feature extraction and adds a separate student mel stage. Build the cache pipeline only after this resolves.

The same caveat applies to vasista22/whisper-hindi-small as student init. If English is gone, initialise from openai/whisper-small and absorb the extra epochs. Worth noting either way: GramVaani telephone audio is already baked into those weights, so dropping telephone data from the corpus doesn't drop it from the model.

Corrections

Two numbers the spec had wrong

  • The mel cache is 80×1000, not 80×500

    Whisper runs at 100 frames per second (hop 160 at 16 kHz), so 30 s is 3000 frames and a 10 s window is 1000. The 500 is the post‑convolution encoder length, one stage later. At 160 KB per clip in fp16 that's 11.5 GB for 72,000 clips rather than 5.8. Comfortable inside the 200 GB private‑dataset quota — just don't provision for the smaller figure.

  • Vaani's 2,043 hours is the transcribed subset, not the corpus

    The full collection is 31,255 hours of audio. The Hindi config of ARTPARK-IISc/Vaani-transcription-part holds 963 hours; all 59 language configs total 234 GB. CC‑BY‑4.0, gated but free — accept terms and pass a token. You want 120 of those 963 hours, so stream with an early stop; pulling the whole config will exhaust the session disk. ai4bharat/IndicVoices is CC‑BY‑4.0 and HF‑hosted, fine as specified.

Execution

Working with the grain of the platform

Nine rules that between them decide whether 108 GPU‑hours of work fits in the quota.

  • Push every non‑GPU stage into CPU notebooks

    Kaggle meters GPU and TPU; CPU notebooks appear not to draw on the 30‑hour pool — confirm this in Gate 0 step 6, because a lot rests on it. CPU sessions give 2× Xeon, 32 GB RAM, 12 hours. Move download, VAD segmentation, resampling, WER filtering, tokenisation, dataset packing, ITN development and eval scoring there. That deletes the “3 GPU hours” prep line outright, along with every minute of prep currently hidden inside a GPU session.

  • Segment to ≤10 s on CPU before labelling

    This ordering is a prerequisite, not a detail. Use silero-vad in the CPU stage. It's what makes the next rule work at all.

  • Fuse pseudo‑labelling and mel precompute into one GPU pass

    You pay GPU time for labelling regardless; mel extraction rides along in dataloader workers. And because a ≤10 s clip's student mel (80×1000) is a prefix of the teacher's 30‑second padded mel, one FFT serves both models. The original plan reads the audio twice; it only needs to once.

  • Every long run is a committed run

    Save & Run All (Commit), never an interactive tab. Interactive sessions idle‑timeout well short of 12 hours; a commit executes headless and you can close the laptop. Print a heartbeat every N steps — long silent cells can trip iopub and per‑cell timeouts even while the GPU is busy.

  • Checkpoint to a private HF Hub repo, not Kaggle output

    /kaggle/working does persist between runs, but it caps around 20 GB and versioning it every 500 steps is clumsy. Use push_to_hub=True, hub_strategy="all_checkpoints", hub_private_repo=True, save_total_limit=1, then resume from the Hub on session start. Put HF_TOKEN in Add‑ons → Secrets, never in the notebook body.

  • Ship the cache as a private Kaggle dataset — sharded

    200 GB private quota, 200 GB per dataset, and a limit of 50 top‑level files. So pack into webdataset tars, or a handful of .npy memmaps plus a parquet index — not 72,000 loose files. Mounts read‑only at /kaggle/input for memory‑mapped reads, exactly as intended.

  • On T4×2, don't use the Trainer default

    It falls back to naive model parallelism and leaves one GPU idle for most of the step. Launch DDP through torchrun or accelerate. This is reported directly by the community Whisper fine‑tuning repos that target Kaggle.

  • Never touch Kaggle TPU

    Importing transformers Trainer or pipeline classes crashes TPU sessions — a known issue, still open. The separate 20 TPU hours per week are simply not usable for this project; don't budget them.

  • Label with CTranslate2, distil with transformers

    Convert the teacher to CTranslate2 and run batched faster-whisper: roughly 4× from the backend plus 2–4× from batching, which takes the 20‑hour labelling line down to 6–10. The caveat that keeps it honest: CT2 returns no logits, so use it for the bulk cross‑entropy labels and keep HF transformers for the 50‑hour KL subset only. int8_float16 is tuned for Ampere and newer; T4 is Turing, so benchmark it against plain float16 on 30 minutes of audio before committing the full pass.

Still under‑costed

Three things the budget doesn't cover

  • Getting the audio in

    200 hours is roughly 12–23 GB compressed and nothing in the plan accounts for the transfer. Reserve a full CPU session for acquisition and assume you'll redo it once after the first attempt hits a disk or rate limit.

  • Disk headroom you haven't printed

    The ~20 GB figure is the output cap; actual session scratch is larger. Run df -h at session start rather than planning around a number nobody has looked at.

  • The 30‑hour YouTube scrape

    Run yt-dlp from the Mac — Kaggle's egress addresses get throttled and blocked in practice. Terms‑of‑service exposure is yours to accept on a personal project; keep the scrape unpublished, or restrict to Creative‑Commons uploads if you want the option of releasing the corpus later.

Sequence

First moves

Each step is cheap and each one can invalidate the next. That's the whole point of the ordering: if step 3 fails on 5 hours it will fail on 200, and you'll have spent one quota‑hour finding out instead of forty.
